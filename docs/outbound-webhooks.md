# Outbound webhook operations

This document is the source of truth for Nexez outbound automation webhooks.
The current integration is compatible with Zapier Webhooks Catch Hook, Make,
n8n, and merchant-owned HTTPS receivers. It is not a native app in the Zapier
Integration Directory.

## Current path and Zapier partner path

The current path is merchant-configured. A merchant creates a Catch Hook in
Zapier and saves that HTTPS URL in Nexez. Nexez sends signed JSON events to the
saved endpoint. It requires no Zapier OAuth grant, partner review, or Zapier app
installation.

A native Zapier partner integration is a separate distribution project. It
requires a Nexez authentication contract for Zapier, named triggers and actions,
stable polling or REST Hook APIs, sample data, field schemas, help content,
versioning, beta users, and Zapier platform review. The native path can appear in
Zapier's app picker and provide guided setup. It does not replace the generic
webhook rail.

## Configuration surfaces

- Listing Settings stores endpoints scoped to one listing. Owners and editors
  can configure them under the owner's Pro entitlement.
- Tools stores account-level endpoints for every supported event across the
  owner's listings.
- Endpoints must be public HTTPS URLs. Literal and DNS-resolved local, private,
  and link-local targets are rejected. Redirects are not followed.
- Each listing supports at most ten endpoint URLs.

For Zapier, use Catch Hook when the Zap only needs the parsed JSON body. Use
Catch Raw Hook when the Zap must inspect `X-Nexez-Signature`.

## Signing-secret lifecycle

Listing secrets are merchant-supplied. Account-level secrets are generated by
Nexez and shown once when the endpoint is created. Both are encrypted with
`INTEGRATION_SECRET_KEY` before database storage. Browser list and settings
responses expose only `hasSecret` or `has_secret`, never plaintext or
ciphertext. Direct browser privileges on the account-level webhook table are
revoked. Delivery workers decrypt the secret immediately before signing.

Nexez sends:

- `X-Nexez-Timestamp: <unix-seconds>`
- `X-Nexez-Signature: t=<unix-seconds>,v1=<hex-hmac>` when a secret exists

The HMAC is SHA-256 over `<timestamp>.<raw-json-body>`. Receivers should reject
stale timestamps and compare the expected signature in constant time.

## Supported events

| Event | Source | Meaning |
| --- | --- | --- |
| `booking.received` | Verified Calendly webhook | A signed Calendly `invitee.created` event was recorded. |
| `booking.canceled` | Verified Calendly webhook | A signed Calendly `invitee.canceled` event was recorded. |
| `booking.provider_redirect` | Nexez checkout runtime | A buyer was handed to the configured provider. This is intent and handoff evidence, not proof of a completed booking. |
| `booking.checkout_initiated` | Nexez checkout runtime | Nexez recorded a supported checkout-initiation signal. This is not settlement proof. |
| `test.webhook` | Settings or Tools | A fixed server-generated connectivity test for an already saved endpoint. |

The event envelope is:

```json
{
  "event": "booking.received",
  "timestamp": "2026-08-25T00:00:00.000Z",
  "page": { "id": "...", "slug": "...", "name": "..." },
  "data": { "source": "calendly" }
}
```

The product must not describe provider redirects or checkout starts as completed
bookings, orders, or settled money.

## Delivery and retries

When Inngest is configured, checkout and Calendly emitters enqueue
`nexez/outbound-webhooks.dispatch`. Each endpoint runs in its own retried step,
with three retries for network errors and non-2xx responses. Successful steps
are memoized. Invalid endpoint configuration is permanent and is not retried.
If event emission fails or Inngest is not configured, the request path uses the
same validated inline delivery code.

Account-level rows retain last delivery time and status. Delivery checks the
owner's entitlement again, so retained endpoints stop receiving events after a
downgrade while remaining removable.

## Release checks

1. Confirm `INTEGRATION_SECRET_KEY`, `INNGEST_EVENT_KEY`, and
   `INNGEST_SIGNING_KEY` are set in the target environment.
2. Save one listing Catch Hook with a signing secret and confirm settings return
   only `hasSecret`.
3. Save one account hook, copy the one-time secret, reload, and confirm the
   plaintext is no longer available.
4. Send fixed tests from both surfaces and verify signatures against the raw
   body.
5. Exercise a checkout handoff and a signed Calendly event, then confirm the
   Inngest runs and account delivery status.
6. Verify private targets, redirects, unsaved test URLs, excessive endpoint
   counts, and downgraded owners fail closed.
